# 글 유형별 템플릿

write-post 스킬 1단계(기획)에서 유형을 정한 뒤 읽는다. 뼈대일 뿐이니 소제목은 글 내용에 맞게 바꾼다. 모든 H2를 같은 형태로 맞추지 않는다.

## 트러블슈팅

예시 글: `posts/react-keepalive-scroll-reset.mdx`

```
## 배경 — 어떤 시스템에서 생긴 일인가
## 증상 — 무엇이 어떻게 안 됐나 (재현 조건)
## 실패한 가설들 — 시도한 것과 왜 아니었나
## 결정적인 측정 — 원인을 확정한 근거
## 해결책 — 코드와 이유
## 교훈 / 결론
```

- 실패한 가설을 지우지 않는다. 독자에게 가장 쓸모 있는 부분이다.
- 측정값(전/후)을 숫자로.

## 딥다이브 · 이전기

예시 글: `posts/chart-library-migration-journey.mdx`, `posts/on-prem-nginx-deployment.mdx`

```
(도입: 문제를 겪은 장면 한 단락)
## Before — 처음 상태와 그때의 선택 이유
## 문제가 생긴 지점
## After — 바꾼 구조, 핵심 코드나 설정
## 놓치기 쉬운 것들
## 결과 — 수치 비교
## 다시 한다면 / 다음 과제
```

- 시간 순서 이야기라면 소제목에 번호를 붙여도 된다. 대신 문장 형태는 섞는다.
- 뒤집은 결정이 있으면 숨기지 않는다.

## 도메인 정리

예시 글: `drafts/semiconductor-equipment-data-essentials.mdx`

```
(도입: 도메인을 몰라서 겪은 실제 장면)
## 항목 1 — 개념 + 화면 설계에 주는 영향
## 항목 2
...
## 마치며 (한두 문단)
## 참고 자료
```

- 항목은 5~6개 이내. 프론트엔드와 바로 닿는 것만.
- 개념은 공개 자료로 확인하고 출처를 맨 아래 모은다.
- 항목마다 직접 겪은 일 한두 문장. 없으면 TODO.
- 정리 표로 다시 요약하지 않는다.

## 회고

예시 글: `posts/hanghae-retrospective.mdx`

```
## 결과 한 줄 (수료, 출시 등)
## 시작할 때
## 기간 중 달라진 것들 (2~4개 섹션)
## 마치며
```

- 감정·관계 이야기도 괜찮다. 대신 구체 장면으로.

## TIL

```
## 무엇을 알게 됐나 (한 단락)
## 예시 코드 또는 재현
## 왜 그런가 (짧게)
## 참고
```

- 300~600단어. 짧게 끝낸다.
